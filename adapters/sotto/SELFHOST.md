# Supervised self-host profiles

For a fresh Railway Photon install, start with the [maintainer source-build helper](../../docs/MAINTAINER-RAILWAY-HELPER.md#self-hosted-on-railway-supervised-sotto-photon).
That helper builds the repository's root `Dockerfile` on Railway from a pinned clean checkout, so it
needs no published image. The operator-file commands below are for a manually managed container
and are not extra steps after the Railway helper runs. Telegram uses the separate one-shot capture
path below; the Railway helper covers Photon only.

## Manual Photon operator file

For self-host Sotto with a Photon Spectrum Cloud project, use `selfhost-photon-operator.json.template` as a root-private operator file outside `/data`. This path uses Photon Cloud credentials (`photonProjectId` and `photonProjectSecret`) and a direct Google model key; it does not start or connect to a local Photon server. Set the owner ID to the owner's E.164 address, set `firstContact.expectedProviderLine` and `photonLineNumber` to the same actual physical Photon line, and set `stableIdentity.projectFingerprint` to SHA-256 of the UTF-8 bytes `sotto-photon-project-v1:` followed by the project ID. Keep the stable tenant, account, line, and volume identifiers consistent across the file. Use distinct runtime, relay, control, Google, and Photon secrets. `receiverAuthority` contains only its listed local capabilities; the model key comes from `modelDirect`, and no model proxy or public receiver attachment is needed.

Protect the operator directory as root:root `0700` and file as root:root `0600`. Use the same production `Dockerfile.runtime` and `Dockerfile.selfhost` image build described below, a dedicated empty ext4 mount at `/data`, root under `tini`, and a private PID namespace. Invoke `python3 -I -B /app/adapters/sotto/selfhost_bootstrap.py --prepare --operator-file /run/sotto/selfhost-photon-operator.json` once on the empty volume. Then start `python3 -I -B /app/adapters/sotto/selfhost_bootstrap.py --run --operator-file /run/sotto/selfhost-photon-operator.json` under `tini` with the same volume, and use that `--run` command for same-volume restarts. The first admitted owner DM on the declared Photon line establishes the activation receipt before scheduled delivery. After activation, literal owner `/loop` task and `/reminder` commands use the same private capability, current Photon route proof, and canonical receiver writers as managed Photon. The direct-model bearer stays in Node's private config.

For a fresh public Railway install, `tools/setup_selfhost_railway.py` supplies a private `SOTTO_SELFHOST_LAUNCH` envelope instead of an operator-file mount. The envelope contains the complete self-host Photon operator bundle and binds its service, `/data` volume receipt, public domain, and setup marker to Railway's injected metadata. The helper builds the root `Dockerfile` (the `Dockerfile.runtime` build plus a root Tini overlay whose default command is `selfhost_bootstrap.py --run`) from the pinned source. Its first deployment's start command is `selfhost_bootstrap.py --prepare`: after fresh preparation, the container serves only `/health` on port 8080 for at most 15 minutes, without starting Node or the receiver. The helper must verify that initializer and its durable preparation receipt before switching the start command to `selfhost_bootstrap.py --run` and deploying the same pinned source again. The latter starts the existing root supervisor on the same volume and never prepares it again. This Railway mode requires a dedicated ext4 `/data` mount and a private PID namespace with `tini` as PID 1; the helper reports uncertain provider or runtime evidence for inspection rather than treating `/health` alone as a usable owner bot.

## Telegram owner bot

The supervised runtime starts a linked Telegram owner bot and the existing five receiver procedures under the same root supervisor, native lock, and restart epoch. Initial linking runs once before this runtime starts. Literal `/loop add <text>`, `/loop close <anchor>`, `/reminder at <ISO8601-with-offset> <text>`, `/reminder list`, and `/reminder cancel <int_id>` use the existing receiver writers. A separate Telegram capability binds the tenant, account, owner, bot fingerprint and fixed private chat; the receiver verifies the protected pairing record and currently loaded Node identity before an operation. Reminder delivery follows the existing proactive cadence. Relinking an active owner or bot is not supported.

This is a **limited self-host Telegram profile**. Its fixed private route, polling, and private owner tasks, reminders, and routines have local contract tests. The current Telegram profile does not mount Photon-only attended meeting prep, owner skill requests, requested briefs, offered replies, brief-detail readback, or staged routine tools. The full attended route profile and entity-aware long-message chunking for chat replies and scheduled output remain deferred. Local tests do not establish live provider delivery; see the [behavior inventory](../../docs/BEHAVIOR-INVENTORY.json) for each claim and its evidence status.

For a new owner whose numeric ID is not yet known, copy `selfhost-setup.json.template` to a root-private file outside `/data`, fill its bot token, random 24–64 character pairing phrase, direct Gemini model, stable local IDs, instructions, timezone, and distinct runtime secrets. Keep its containing directory root:root `0700` and the file root:root `0600`. On an empty dedicated ext4 `/data` mount, invoke `python3 -I -B /app/adapters/sotto/selfhost_setup.py --setup-file /run/sotto/selfhost-setup.json --operator-file /run/sotto/selfhost-operator.json` under `tini` in a private PID namespace. The setup takes a nonblocking lock on the `/data` directory for the whole capture and preparation, so a competing setup cannot poll the same bot. It prints a Telegram deep link to its private operator log, waits for the intended owner to send `/start <phrase>`, and uses the existing linker to capture and confirm that owner. It then writes the protected operator file and **runs fresh preparation itself**. A timeout or unconfirmed Telegram update leaves `/data` untouched. Preserve the capture and operator files outside `/data` for review and later starts; run the image's default `--run` command with that operator file after successful preparation. An existing capture or operator output is refused by setup; a capture left by an interrupted attempt requires operator review before a fresh pairing attempt. A changed owner or bot on an active volume is not a restart operation.

For a separately prelinked owner, copy `selfhost-operator.json.template` to a private path such as `/run/sotto/selfhost-operator.json`, fill every placeholder, and protect the containing directory as root:root `0700` and the file as root:root `0600`. Keep the file outside `/data`; it contains bot, model, and runtime credentials. Set `telegramLink.allowed_user` to the numeric owner ID, repeat the exact token in `telegramLink.bot_token` and `credentials.telegramToken`, and set `stableIdentity.botFingerprint` to SHA-256 of the UTF-8 bytes `sotto-telegram-bot-v1:` followed by that token. The tenant and volume IDs are operator chosen stable local IDs and must match throughout the input. Use distinct secrets for the runtime bearer, relay root, control token, direct Gemini key, and Telegram bot.

Build the production runtime image from `Dockerfile.runtime`, then build `Dockerfile.selfhost` with that reviewed image digest as `RUNTIME_IMAGE`. The self-host image defaults to `selfhost_bootstrap.py --run --operator-file /run/sotto/selfhost-operator.json`. It requires a dedicated, truly empty ext4 filesystem mounted at `/data` in the container, the private operator file mounted at the declared path, root execution under `tini`, and an otherwise private PID namespace. A regular directory or an already populated volume is rejected.

Only for this manually prelinked path, invoke `python3 -I -B /app/adapters/sotto/selfhost_bootstrap.py --prepare --operator-file /run/sotto/selfhost-operator.json` once on a new empty volume. The initial-link setup above already performs this step; the two installation commands are mutually exclusive for one volume. Start the default `--run` command with the same operator file and attached volume. On a supervised same-volume restart, use `--run` again; the verified hold and epoch determine reentry. Do not rerun either preparation command on an existing volume. The bootstrap observes the live `/data` mount, validates the complete handoff, clears ambient variables before starting either role, and removes its temporary derived operator file when the supervisor exits.

The supervisor passes one descriptor for the receiver's private setup-link boot line; general
receiver and Node output stay suppressed. Keep deployment logs private. Self-host operator bundles
may explicitly set `receiverOverrides.SOTTO_BACKGROUND_UNMETERED` to the string `true` or `false`.
Omitted/false leaves background history learning held before source reads; true permits uncapped
direct-key background learning after source consent. The public Railway helper accepts the
equivalent optional `sotto_runtime.background_unmetered` JSON boolean, default false. Ambient
variables are never forwarded. An explicit `SOTTO_TIMEZONE` fixes the installation zone, and a
conflicting timezone setter is rejected without changing stored settings. Both choices are part of
the installation's identity and epoch binding, so changing either means a fresh installation.

## Owner nudge pause

After owner activation/linking, send `/quiet for 2h` or `/quiet for 90m` to pause nudges, including due one-time reminders. Send `/quiet off` to clear that temporary pause. Durations must be positive integer hours or minutes, at most 24 hours. Briefs continue; ordinary quiet hours still apply. Due owner reminders can resume on a later proactive tick after the pause clears, while ordinary held inbound events keep their existing digest/brief behavior. Acknowledgments record the admitted command; duplicate messages and receipt recovery do not extend the pause. This does not enable other preference writes.

You can also request an unconditional one-time reminder in a single ordinary message. Sotto uses the configured timezone and asks when the day or time is ambiguous; it records a clear private reminder without asking for a second approval. Its acknowledgement includes the recorded reminder ID and due time. Use `/reminder list` or `/reminder cancel <int_id>` to manage it. Delivery follows the normal proactive cadence and quiet rules, so the requested minute is not an exact delivery guarantee. This does not schedule recurring or conditional work or authorize external actions. Combined multi-message turns currently need one clear reminder request in a single message.

### Private tasks in ordinary chat

You can ask to add a task in your own words, or say that a specific task you created is done.
The assistant uses your exact wording for a new task and asks when the task to close is unclear.
An explicit private correction needs no second confirmation. Each message supports one task or
reminder change. Task creation and completion also remain available through the existing
`/loop add` and `/loop close` commands. These task tools do not close obligations inferred from
your sources, perform bulk cleanup, or send messages to anyone else. If a write's result is
uncertain, the assistant checks the existing result before acknowledging it; it does not repeat
the write, and other safe chat can continue.
